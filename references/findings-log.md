# 发现日志工作流（FINDINGS 双轨）

> 借鉴 Modex/WorkBuddy 的 FINDINGS_TEMPLATE 设计（逆向学习 2026-08-14），
> 适配本技能的证据纪律。对应 research-cycle 的 D2/D3/D4.5 阶段。

## 为什么需要

- **ROUND_R 是修改记录**（变更/原因/验证），不是发现日志。
- 实验/审稿/调试产生**跨阶段的洞见与教训**，不记录会在会话间丢失——
  下个会话重复同样的错误或错过重要信号（FM-22 环境锁、FM-29 训练配置的教训
  都是"事后才记录"的例子，FINDINGS 应即时记）。

## 结构

```
FINDINGS.md
├── # Research Findings（研究洞见）
│   每段: [日期] 主题 / 发现 / 证据(文件+字段) / 影响(如何改变声明)
└── # Engineering Findings（工程教训）
    每段: [日期] 主题 / 问题与根因 / 修复 / 防复发机制
```

## 何时写（MUST follow）

1. **研究洞见**：实验发现有效/无效/为何；Reflector/审稿人指出方法缺陷；
   决策改变声明或实验设计。
2. **工程教训**：修复 bug、环境陷阱（下载/显存/路径）、调试根因。
3. **即时写**：完成实质工作后立即追加（与 FM-24 重建 manifest 同节奏），
   不等轮次结束。

## 何时读

- **session 恢复先读**：新会话开始工作前扫 FINDINGS.md 近 3 天条目
  （比 ROUND_R 更适合恢复上下文）。
- **审稿前读**：对抗审稿 D4.5 前扫一遍，避免重复提出已记录的已知问题。

## 纪律

1. **append-only**：追加不覆盖；每天一段。
2. **Research 与 Engineering 分开**：研究洞见影响科学声明，工程教训影响复现。
3. **链接证据**：每条引用具体文件/行/字段（可追溯，与 claim ledger 同源）。
4. **与失败模式库联动**：Engineering 发现中的防复发机制 → 沉淀为 FM 条目
   （FM-29 即此流程的产物）。
5. **与 ROUND_R 分工**：ROUND_R = 修改记录（变更/原因/验证）；FINDINGS = 发现
   日志（洞见/教训/决策）。两者互补，不重复。
